# Золотой конспект: продвинутый JPA (транзакции)

> Второй уровень JPA — то, что отличает middle от «читал про транзакции». Изоляция, блокировки, propagation, persist/merge. Формат: боль → механизм → формула на собес. Читай, закрывай, вспоминай.

## 1. ⭐ Уровни изоляции и аномалии

**Проблема:** транзакции работают **одновременно** и портят данные друг другу. Изоляция = насколько транзакция защищена от вмешательства соседей.

> Фундаментальный компромисс: **выше изоляция = больше корректности, но меньше параллелизма** (транзакции ждут). Уровни — это ползунок «безопасно/медленно ↔ быстро/опасно».

### Три аномалии (по нарастанию тонкости)

**Dirty read (грязное чтение)** — читаешь **незакоммиченное** чужое, которое может откатиться:
```
A: UPDATE balance=0 (НЕ закоммичено)
B: SELECT balance → 0
A: ROLLBACK → B прочитала значение, которого никогда не было
```

**Non-repeatable read (неповторяющееся чтение)** — та же строка **изменилась** между двумя чтениями (B закоммитилась):
```
A: SELECT balance → 100  (проверка: хватает на снятие 80)
B: UPDATE balance=50, COMMIT
A: SELECT balance → 50   (действую... но уже 50 → минус)
```
Проблема: транзакция проверяет по одному значению, действует по другому.

**Phantom read (фантомное чтение)** — появились/исчезли **строки** в выборке между запросами:
```
A: SELECT COUNT(*) WHERE client_id=1 → 4  (правило: max 5 счетов, ок)
B: INSERT новый счёт, COMMIT
A: снова COUNT → 5, но обе транзакции решили "можно" → 6 счетов, инвариант нарушен
```

| Аномалия | Что происходит | B закоммитилась? |
|---|---|---|
| **Dirty read** | читаешь незакоммиченное | нет |
| **Non-repeatable** | существующая строка изменилась | да |
| **Phantom** | новые/удалённые строки в выборке | да |

> Суть всех трёх: транзакция принимает решение на данных, которые меняются под ногами.

### Четыре уровня (каждый запрещает на одну аномалию больше)

| Уровень | Dirty | Non-repeatable | Phantom |
|---|---|---|---|
| **READ_UNCOMMITTED** | ❌ | ❌ | ❌ |
| **READ_COMMITTED** | ✅ | ❌ | ❌ |
| **REPEATABLE_READ** | ✅ | ✅ | ❌* |
| **SERIALIZABLE** | ✅ | ✅ | ✅ |

**Дефолты (спрашивают):** PostgreSQL / Oracle → **READ_COMMITTED**. MySQL (InnoDB) → **REPEATABLE_READ**.

`*` По стандарту REPEATABLE_READ разрешает фантомы, но PostgreSQL (MVCC) и MySQL (gap-locks) на практике от них защищают — реализация строже стандарта.

```java
@Transactional(isolation = Isolation.REPEATABLE_READ)
public void transfer(...) { ... }
```

### ⭐ Механизм: MVCC vs блокировки

Как REPEATABLE_READ даёт стабильное чтение — два разных способа:

**MVCC (Multi-Version Concurrency Control) — PostgreSQL, Oracle:**
> Транзакция читает из **снимка (snapshot)** на момент старта. БД не перезаписывает строку при UPDATE, а создаёт **новую версию**; старая остаётся. Транзакция видит только версии из своего снимка → чужие коммиты не видны.

```
balance=100 (версия T10)
A стартует → снимок
B: UPDATE balance=50, COMMIT → создана НОВАЯ версия (50)
A: SELECT → всё ещё видит СВОЮ версию (100), версия B новее снимка → игнорит
```
Лозунг: **«readers don't block writers, writers don't block readers»**. При своей записи в изменённую строку → `could not serialize access` → retry.

**Блокировки — MySQL / явные locks:**
> Транзакция блокирует строку (shared lock) при чтении; другие ждут, пока не закончится.

| | MVCC (снимок) | Блокировки |
|---|---|---|
| Читатель мешает писателю | **нет** | да (ждёт) |
| Скорость | выше | ниже |
| Где | PostgreSQL, Oracle | MySQL, явные locks |

**Проверь себя:**
1. Три аномалии — назови и отличи (dirty vs non-repeatable vs phantom).
2. Четыре уровня — какой что запрещает? Дефолты PostgreSQL и MySQL?
3. Как MVCC даёт стабильное чтение? За счёт чего A видит старое значение?

## 2. ⭐ Блокировки: optimistic vs pessimistic

**Проблема — lost update (потерянное обновление):**
```
balance=100
A: читает 100 → 100+50=150, save → 150
B: читает 100 → 100-30=70,  save → 70
→ пополнение на 50 ПРОПАЛО (должно 120, стало 70)
```
Два конкурентных изменения, одно затирает другое. Блокировки это предотвращают — двумя подходами.

### Оптимистичная (`@Version`)

**Философия:** конфликты редки → не блокирую, **проверяю версию при записи**.

```java
@Entity
class Account {
    @Id UUID id;
    BigDecimal balance;
    @Version Long version;   // Hibernate сам инкрементит
}
```

```
balance=100, version=5
A: читает v5 → UPDATE ... SET balance=150, version=6 WHERE id=1 AND version=5 → ок (v6)
B: читает v5 → UPDATE ... WHERE id=1 AND version=5 → 0 строк! (в БД уже v6)
   → 💥 OptimisticLockException → retry (перечитать v6, повторить)
```
Магия в `WHERE version=?`: если версия сменилась — UPDATE не находит строку → конфликт пойман. Lost update предотвращён.

### Пессимистичная (`FOR UPDATE`)

**Философия:** конфликты часты → **блокирую строку сразу** при чтении.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT a FROM Account a WHERE a.id = :id")
Account findByIdForUpdate(@Param("id") UUID id);   // → SELECT ... FOR UPDATE
```
```
A: SELECT FOR UPDATE → блокирует строку, читает 100
B: SELECT FOR UPDATE → ЖДЁТ (заблокировано)
A: 150, COMMIT → замок снят
B: читает 150 (свежее!), 150-30=120 ✅
```
- **PESSIMISTIC_WRITE** — эксклюзив (`FOR UPDATE`);
- **PESSIMISTIC_READ** — shared (другие читают, не пишут).

### ⭐ Выбор (это спрашивают)

| | Оптимистичная | Пессимистичная |
|---|---|---|
| Блокировка | нет | да (замок) |
| Другие транзакции | не ждут | **ждут** |
| Конфликт | `OptimisticLockException` → retry | не пускает |
| Скорость | быстрее | медленнее |
| Риск | retry storm | deadlock, ожидание |
| Когда | **редкие** конфликты | **частые** конфликты / горячая строка |

**⭐ Retry storm — ключевой инсайт:** оптимистичная на **горячей** строке защитит (корректность есть), но **развалится по производительности**: только одна транзакция за раунд побеждает, остальные откатываются и повторяют → шторм ретраев, впустую потраченная работа, starvation. Поэтому на горячих строках — пессимистичная (очередь: каждый проходит раз).

> Выбор = «какая **дешевле** при данной частоте конфликтов», а не «какая защитит» (защитят обе). Редко → оптимистичная. Часто → пессимистичная.

**Третий путь** (за пределами must-have): атомарный `UPDATE ... SET balance = balance - 30 WHERE balance >= 30` — БД сама атомарно, без блокировок в приложении.

**Проверь себя:**
1. Что такое lost update?
2. Как `@Version` ловит конфликт (что в WHERE)?
3. Почему оптимистичная плоха на горячей строке (retry storm)?

## 3. ⭐ Propagation (распространение транзакций)

**Проблема:** `@Transactional`-метод зовёт другой `@Transactional`-метод. Что делать — общая транзакция или отдельная? Откатывать ли внешнюю, если упала внутренняя?

**Propagation** = как транзакционный метод ведёт себя внутри уже существующей транзакции.

### REQUIRED (дефолт) — «присоединись или создай»

Есть транзакция → присоединиться. Нет → создать. **Всё в одной транзакции.**
```
outer() открыл T1
  inner() → присоединился к T1
  → коммит/откат ВМЕСТЕ
```
> inner упал → откатится **вся** T1 (общая судьба). 90% случаев.

### REQUIRES_NEW — «всегда своя, приостанови внешнюю»

Всегда новая отдельная транзакция; внешняя **приостанавливается** (suspend).
```
outer() открыл T1
  inner() → приостановил T1, открыл T2
  inner() коммитит T2 НЕЗАВИСИМО
  → вернулись в T1
```
> ⭐ T2 коммитится **отдельно**: если T1 потом откатится — T2 уже сохранена. Кейс: **аудит/лог попытки должен остаться, даже если основная операция откатилась.**
> ⚠️ Цена: приостановленная T1 держит своё соединение → **два коннекта** одновременно. В цикле → исчерпание пула.

### NESTED — «savepoint внутри внешней»

Вложенная под-транзакция через **savepoint**.
```
outer() открыл T1
  inner() → SAVEPOINT в T1
  inner() упал → откат ТОЛЬКО до savepoint, T1 жива, outer продолжает
```
> inner может откатиться **отдельно** (частичный откат), НО зависит от outer: если T1 откатится — inner тоже. Кейс: батч, где сбой одной строки не рушит весь. ⚠️ Нужен savepoint-драйвер (не везде).

### ⭐ Сравнение

| | Новая тр.? | inner упал → outer | outer откатился → inner |
|---|---|---|---|
| **REQUIRED** | нет (присоединяется) | **тоже откат** | тоже откат |
| **REQUIRES_NEW** | **да, отдельная** | outer **выживает** | inner **выживает** (закоммичен) |
| **NESTED** | нет (savepoint) | outer **выживает** | inner тоже откат |

> **REQUIRED** — общая судьба. **REQUIRES_NEW** — полная независимость. **NESTED** — inner зависит от outer, но не наоборот.

### Остальные 4 (знать названия)
- **SUPPORTS** — есть тр. → в ней, нет → без транзакции;
- **NOT_SUPPORTED** — выполнить вне транзакции;
- **MANDATORY** — требует существующую, иначе исключение;
- **NEVER** — запрещает транзакцию, иначе исключение.

> ⚠️ Работает **через прокси** → self-invocation (вызов `this.inner()` изнутри класса) **игнорирует** propagation.

**Быстрый выбор:** «если внешняя откатится, должна ли внутренняя работа сохраниться?» да → REQUIRES_NEW; нет → REQUIRED; откатиться самой, но не рушить внешнюю → NESTED.

**Проверь себя:**
1. REQUIRED vs REQUIRES_NEW vs NESTED — два вопроса (inner упал→outer? outer упал→inner?).
2. Зачем REQUIRES_NEW для аудита?
3. Что ломает propagation (self-invocation)?

## 4. persist vs merge vs save vs saveAndFlush

Четыре «сохранения», работают с разными состояниями (transient/detached).

### persist() — JPA, для НОВЫХ

> Берёт **transient** объект → делает **managed** (привязывает к контексту). void, всегда INSERT. Detached → исключение. Модифицирует **переданный** объект.

```java
Employee e = new Employee();   // transient
em.persist(e);                  // теперь managed (тот же объект)
```

### merge() — JPA, для DETACHED

> Берёт **detached** → **копирует состояние** в managed-сущность → **возвращает** managed-копию. Переданный остаётся **detached**.

```java
Employee managed = em.merge(detached);
managed.setSalary(...);    // ✅ сохранится
detached.setSalary(...);   // ❌ НЕ сохранится (всё ещё detached!)
```
> ⚠️ Главный баг: работать с исходным объектом после merge. Надо — с **возвращённым**.

### ⭐ persist vs merge

| | persist | merge |
|---|---|---|
| Состояние | transient | detached (и новый) |
| Возвращает | void | **managed-копию** |
| Переданный объект | становится managed | остаётся detached |
| Detached на вход | исключение | работает |

### save() — Spring Data, обёртка

```java
if (isNew(entity)) em.persist(entity);   // новый (id=null) → persist
else return em.merge(entity);             // существующий → merge (возвращает копию!)
```
> Определяет новизну по `@Id`. Для существующих зовёт merge → **возвращает копию**, используй `saved = repository.save(e)`, не исходный.

### saveAndFlush() — save + немедленный flush

> `save` копит SQL до flush/коммита. `saveAndFlush` форсирует SQL **сразу**. Нужен: сгенерированный id немедленно / последующий JPQL должен увидеть изменения / тесты.

### Связь с жизненным циклом
```
new()  ──persist()──►  managed  ──транзакция закрылась──►  detached
       detached ──merge()──► НОВАЯ managed-копия
```

## Что дальше по маршруту

JPA закрыт **полностью** (базовый + механики + продвинутый). Следующий большой блок под банковский собес:
- **Многопоточность** — `synchronized`, `volatile`, happens-before, `ConcurrentHashMap`, пулы потоков, `CompletableFuture`. Спрашивают почти всегда.
- **Collections внутри** — HashMap (бакеты, resize), ArrayList vs LinkedList.
- **JVM/GC**, **SQL напрямую** (джойны, индексы, план запроса).
