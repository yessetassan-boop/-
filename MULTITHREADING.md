# Золотой конспект: Многопоточность (Java Concurrency)

> Вся многопоточка для банковского собеса. Формат: **боль → механизм → формула на собес**. Сквозная метафора — **склад с работниками** (процесс = склад, потоки = работники, общие данные = общий ящик). Многое пересекается с конкурентностью в JPA — связи отмечены. Читай, закрывай, вспоминай.

---

## 0. Главная идея всей темы

> **Многопоточность даёт скорость (параллельность), но платишь сложностью и риском гонок.** Вся тема — про то, **как безопасно работать с общими изменяемыми данными**.

**Race condition возникает при ДВУХ условиях сразу:** данные **общие** + хотя бы один поток **пишет**. Только чтение общего — безопасно.

Три пути к безопасности (убрать одно из условий):
1. убрать **общность** (свой ящик каждому — thread-local, копии);
2. убрать **изменяемость** (immutable-данные);
3. **синхронизировать** доступ (замок на ящик — synchronized, atomic).

---

## 1. Процесс vs Поток

- **Процесс** — запущенная программа со **своей изолированной** памятью (склад-здание).
- **Поток** — линия выполнения **внутри** процесса; потоки **делят память** процесса (работники в одном складе).

| | Процесс | Поток |
|---|---|---|
| Память | своя, изолированная | **общая** с другими потоками |
| Создание | дорого | дёшево |
| Общение | сложно (IPC) | легко (общая память) → но отсюда гонки |
| Крах | не влияет на другие | может уронить весь процесс |

> **Почему гонки — проблема потоков, а не процессов:** потоки делят память (общий склад) → возможны общие данные. Процессы изолированы (разные здания) → чужую память не тронуть → гонки нет.

```java
Runnable task = () -> System.out.println("работаю");
new Thread(task).start();   // ⚠️ start() — новый поток; run() — просто вызов в текущем!
```

> ⚠️ `start()` запускает **новый** поток. `run()` — просто вызывает метод **в текущем** потоке (никакой многопоточности).

**Проверь себя:** почему два процесса не устроят гонку над переменной, а два потока — да? Разница start() vs run()?

## 2. ⭐ Race condition (состояние гонки)

**Главный секрет:** `count++` — это **НЕ одна операция, а ТРИ** (read-modify-write):
```
1. ЧИТАЙ count из памяти
2. ИЗМЕНИ (+1)
3. ЗАПИШИ обратно
```
Между этими шагами **влезает другой поток**:
```
count=5
A читает → 5
B читает → 5      ← влез между шагами A
A пишет 6
B пишет 6         ← работал со своей 5, затёр A
→ count=6, а должно 7. ОДИН ИНКРЕМЕНТ ПОТЕРЯН.
```

> **= lost update из JPA**, но на уровне памяти, а не БД. Одна болезнь, разные уровни.

**Race condition** — результат зависит от **порядка** выполнения потоков (недетерминированного) → непредсказуемость.

**Почему коварен:** проявляется **не каждый раз** (зависит от планировщика) → на твоей машине «работает», в тестах зелено, в проде под нагрузкой — баг раз в тысячу операций. **Нельзя поймать тестом надёжно → надо предотвращать дизайном.**

**Критическая секция** — код с общими данными, где должен быть **один поток за раз**.

**Три условия гонки:** общие данные + запись + **неатомарность** (несколько шагов). Убери любое → гонки нет.

> **Атомарность убивает гонку:** неделимая операция не имеет «середины», куда влезть. Нет промежутка → нет гонки.

**Проверь себя:** почему count++ — три операции? Почему гонку нельзя поймать тестом? Что такое критическая секция? Как атомарность убивает гонку?

## 3. ⭐ Visibility, volatile, happens-before

**Новая проблема (НЕ гонка!):** поток может **вообще не увидеть** изменение другого потока — работает со старым значением, возможно вечно.

**Механизм — кэши ядер:**
```
      [ Основная память (RAM) ]
         ↑              ↑
   [ кэш ядра 1 ]  [ кэш ядра 2 ]   ← каждое ядро копирует переменную в СВОЙ кэш
         ↑              ↑
     Поток A        Поток B
```
Поток пишет в свой кэш → другой поток читает из своего кэша (старое значение) → изменение «застряло», не видно. Метафора: у каждого работника своя записная книжка (кэш), смотрят в неё, а не на общую доску.

> ⚠️ Это **НЕ race condition.** Гонка — «оба пишут, затирают». Видимость — «один пишет, другой не видит вообще».

**`volatile`** — «не кэшируй, читай/пиши в основную память напрямую» → гарантирует **видимость** (запись сразу видна всем).
```java
private volatile boolean running = true;   // изменение из другого потока сразу видно
```

> ⭐ **`volatile` НЕ даёт атомарности!**
> ```java
> volatile int count;  count++;   // ВСЁ ЕЩЁ гонка — три шага остались
> ```
> volatile решает **видимость**, но `count++` — составная операция, между шагами всё равно влезают. Для неё нужен synchronized/atomic.

**⭐ Водораздел (это отличает понимающего):** дело **не в типе данных**, а в **типе операции**:
- **простое присваивание** (`flag=true`, `count=10`, любого типа) → volatile **хватает** (само атомарно, нужна только видимость);
- **read-modify-write** (`count++`, даже `b=!b` у boolean!) → volatile **НЕ хватает**, нужна синхронизация.

**happens-before** — правило JMM: если A happens-before B, то результат A **гарантированно виден** в B. Создаётся: **volatile** (запись→чтение), **synchronized** (выход→вход), **Thread.start()**, **Thread.join()**. Отсюда их гарантии видимости.

**Проверь себя:** что такое visibility и почему возникает (кэши)? volatile решает видимость или атомарность? Водораздел «присваивание vs read-modify-write»? Что такое happens-before?

## 4. ⭐ synchronized и блокировки

**Идея:** сделать критическую секцию неделимой **замком** — один поток внутри, остальные ждут.

```java
public synchronized void increment() { count++; }   // замок на весь метод
// = 
public void increment() {
    synchronized (this) { count++; }                 // замок на монитор this
}
```

**Монитор** — у каждого объекта есть встроенный замок. `synchronized`-метод захватывает монитор `this`.
> Два потока блокируют друг друга, **только если синхронизируются на ОДНОМ объекте.** Разные объекты — разные замки — не мешают.

**Блок vs метод:** блок **лучше** — держи замок минимально (короткая критическая секция = короткая очередь). Синхронизировать весь метод, когда опасна одна строка — расточительно.

**На чём синхронизироваться:** `private final Object lock` (best practice) — не `this` (внешний код может захватить), не String/Integer (кэшируются).

**static synchronized** — замок на **класс** (`Counter.class`), не на инстанс. С обычным synchronized **не пересекается** (разные замки).

### ⭐ Deadlock (взаимная блокировка)
```java
Поток 1: synchronized(A) { synchronized(B) {...} }   // держит A, ждёт B
Поток 2: synchronized(B) { synchronized(A) {...} }   // держит B, ждёт A
→ оба ждут вечно. DEADLOCK.
```
Метафора: два человека в коридоре, каждый уступает «после вас» — стоят вечно.

**4 условия (Коффман, нужны все):** взаимное исключение + удержание с ожиданием + нет вытеснения + **круговое ожидание**.

**Как избежать:** **захватывай замки в ОДНОМ порядке** (оба A→B, никогда крест-накрест) → нет цикла → нет deadlock. Ещё: `tryLock` с таймаутом, меньше вложенных замков.

> **= пессимистичная блокировка из JPA** (`SELECT FOR UPDATE`): замок + очередь. Deadlock бывает и в БД.

**Проверь себя:** на чём висит замок synchronized? Блок или метод — что лучше и почему? Что такое deadlock и как избежать?

## 5. ⭐ Atomic и CAS

**Проблема synchronized:** проигравший поток **засыпает** (блокируется) → дорого. Можно ли атомарно без блокировки?

**CAS (Compare-And-Swap)** — атомарная инструкция процессора:
> **CAS(ожидаемое, новое):** если текущее значение == ожидаемому → замени на новое (успех); иначе → неудача (кто-то изменил). Всё одной неделимой инструкцией.

Атомарный инкремент:
```
читаю 5 → вычисляю 6 → CAS(ожидаю 5, ставлю 6):
  в памяти 5 → ставит 6 ✅
  в памяти 7 (влезли) → неудача → ПОВТОР с новым значением
```

> ⭐ **= оптимистичная блокировка `@Version` из JPA!**
> `UPDATE ... WHERE version=5` ≡ `CAS(ожидаю 5, ставлю 6)`. Не совпало → retry. Одна идея на уровне БД (@Version) и памяти (CAS).

```java
AtomicInteger count = new AtomicInteger(0);
count.incrementAndGet();      // атомарный ++ через CAS, БЕЗ блокировки (lock-free)
count.compareAndSet(5, 6);    // сам CAS
```
Семейство: `AtomicInteger`, `AtomicLong`, `AtomicBoolean`, `AtomicReference<T>`.

**Lock-free:** проигравший поток **не засыпает**, а **сразу повторяет** → дёшево (нет переключения контекста).

**⭐ Trade-off (тот же, что optimistic/pessimistic в JPA):**
- **редкие конфликты** → CAS/atomic быстрее (нет блокировок);
- **высокая конкуренция** на одну переменную → **retry storm** (постоянные повторы жгут CPU) → тут `synchronized` (очередь) лучше.

**ABA-проблема:** значение A→B→A, CAS видит «A==A, ок», не заметив промежутка. Решается версией (`AtomicStampedReference` — как @Version).

**Проверь себя:** что такое CAS? Чем atomic отличается от synchronized (что с проигравшим потоком)? Связь с @Version? Что такое retry storm и ABA?

## 6. ⭐ Concurrent-коллекции

**HashMap НЕ потокобезопасен** — теряет данные, при одновременном resize мог **зациклиться** (100% CPU, клал серверы). В потоках — нельзя.

**Эволюция потокобезопасных мап = дробление замка:**

| | Гранулярность замка | Параллелизм |
|---|---|---|
| **synchronizedMap / Hashtable** | вся мапа (1 замок) | 1 поток за раз |
| **ConcurrentHashMap (Java 7)** | сегмент (16 замков) | до 16 потоков |
| **ConcurrentHashMap (Java 8+)** | **бакет** + CAS + lock-free чтение | максимум |

> **Принцип: чем мельче замок, тем меньше потоков ждут зря.** Замок = очередь; большой замок = длинная очередь даже к разным данным. CHM Java 8+: замок только на затронутый бакет, вставка в пустой — через CAS (lock-free), чтение — без замков.

**Свойства ConcurrentHashMap:**
- чтение почти без блокировок, запись блокирует только бакет;
- **null запрещён** (ключ и значение) — неоднозначность «нет ключа vs null-значение» в многопотоке;
- атомарные методы: `putIfAbsent`, `merge`, `compute`, `computeIfAbsent`.

**⭐ Составные операции — гонка ДАЖE в CHM:**
```java
if (!map.containsKey(k)) map.put(k, v);   // ❌ между containsKey и put влезут
map.putIfAbsent(k, v);                     // ✅ атомарно

map.put(k, map.get(k)+1);                  // ❌ lost update
map.merge(k, 1, Integer::sum);             // ✅ атомарный инкремент
```
> CHM делает **каждый метод** атомарным, но **комбинацию** — нет. `merge`/`compute` — пересчёт существующего; `putIfAbsent`/`computeIfAbsent` — вставка если нет.

**⭐ CHM защищает МАПУ, но НЕ значения внутри:**
```java
ConcurrentHashMap<String, ArrayList<String>>   // ArrayList внутри — НЕ потокобезопасен!
map.get("k").add(x);   // гонка внутри add() на общем ArrayList
// фикс: CopyOnWriteArrayList внутри, или map.compute(...) с модификацией
```

**Другие:**
- **CopyOnWriteArrayList** — при записи копирует весь массив; чтение без блокировок. Для **read-heavy списков** (редкая запись). Частая запись → катастрофа (копирование).
- **BlockingQueue** — `take()` ждёт если пусто, `put()` ждёт если полно. Основа producer-consumer и пулов потоков.

**Проверь себя:** почему HashMap опасен? Чем CHM быстрее synchronizedMap (дробление замка)? Гонка в составных операциях — как чинить? CHM защищает значения внутри?

## 7. ⭐ Пулы потоков: ExecutorService, CompletableFuture

**Проблема `new Thread()` на каждую задачу:**
- поток дорогой (~1 МБ стек + создание); 10 000 задач = 10 000 потоков = OOM;
- неконтролируемо (сколько потоков? CPU захлёбывается в context switch);
- нет переиспользования.

**Пул потоков** — фикс. число потоков перемалывает **очередь задач**, переиспользуясь. Метафора: бригада из 10 работников разбирает 5000 коробок (не 5000 работников). = аналог **connection pool** к БД.

```java
ExecutorService executor = Executors.newFixedThreadPool(10);
executor.submit(() -> handle(req));   // задача в очередь, свободный поток возьмёт
executor.shutdown();                   // ⚠️ обязательно закрыть
```

**Виды:** `newFixedThreadPool(n)` (основной), `newCachedThreadPool` (по надобности), `newSingleThreadExecutor` (1 поток), `newScheduledThreadPool` (по расписанию).

> ⚠️ В проде — **`new ThreadPoolExecutor(...)`** напрямую, не `Executors`: у `Executors.newFixedThreadPool` **неограниченная очередь** → перегрузка копит задачи до OOM. Ручной позволяет задать размер очереди и политику отказа.

**Future** — «обещание результата»:
```java
Future<Integer> f = executor.submit(() -> compute());
Integer result = f.get();   // ⚠️ БЛОКИРУЕТ поток до готовности
```

**⭐ CompletableFuture** — цепочки асинхронных операций **без блокировки**:
```java
CompletableFuture.supplyAsync(() -> fetchUser(id))   // асинхронно
    .thenApply(user -> user.getEmail())               // когда готово → преобразуй
    .thenAccept(email -> send(email));                // когда готово → используй
// ничего НЕ блокирует; каждый шаг по готовности предыдущего
```
Объединение параллельных задач:
```java
userF.thenCombine(accF, (u, a) -> new Profile(u, a));  // оба запроса ПАРАЛЛЕЛЬНО, объединить когда оба готовы
```

> **Future.get() vs CompletableFuture:** оба про асинхронные задачи. Разница в получении результата: `get()` **блокирует** поток (простаивает); CompletableFuture строит **неблокирующую** цепочку «когда готово → сделай», поток свободен.

Методы: `supplyAsync`, `thenApply` (преобразовать), `thenCompose` (связать асинхронно), `thenCombine` (объединить два), `exceptionally`/`handle` (ошибки).

> **Связь со Spring:** `@Async` под капотом использует ExecutorService, может возвращать CompletableFuture.

**Проверь себя:** зачем пул (2 проблемы new Thread)? Future.get() vs CompletableFuture — что с потоком (блокирует/нет)? Почему в проде ThreadPoolExecutor, а не Executors?

## Связи с JPA (твоя фора)

| Многопоточность | JPA |
|---|---|
| race condition (count++) | lost update (два перевода) |
| synchronized (замок+очередь) | пессимистичная блокировка (FOR UPDATE) |
| CAS (проверь-при-записи→retry) | оптимистичная блокировка (@Version) |
| retry storm на atomic | retry storm на @Version (горячая строка) |
| deadlock (крест-накрест замки) | deadlock транзакций в БД |

> Конкурентность — одна теория на двух уровнях: **память (потоки)** и **БД (транзакции)**. Ты уже знал половину из JPA.
