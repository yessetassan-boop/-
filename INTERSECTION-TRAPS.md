# Золотой конспект: стыковые ловушки (Collections × JVM × Concurrency)

> Это не повтор основ (они в COLLECTIONS-JVM.md и MULTITHREADING.md) — это **пять конкретных ловушек**, всплывших в разборе реальных вопросов, где темы пересекаются. Именно на таких стыках чаще всего спотыкаются на собесе. Формат: код → в чём ловушка → правильный ответ.

---

## 1. ⭐ HashMap хеширует только КЛЮЧИ, не значения

```java
Map<String, Product> catalog = new HashMap<>();
catalog.put(p.getSku(), p);         // p — ЗНАЧЕНИЕ, ключ — String sku
p.setPrice(new BigDecimal("80"));   // у Product mutable hashCode (sku+price)
catalog.get("SKU-001");             // ✅ НАЙДЁТ, несмотря на mutable hashCode у Product!
```

**Почему находит:** `HashMap.get()` вызывает `hashCode()`/`equals()` **только у ключа**. Ключ тут — `String` (immutable) → его хеш никогда не меняется → бакет всегда тот же. То, что происходит внутри `Product` (значения) — HashMap вообще не касается.

**Контраст — когда ЭТО ЖЕ mutable-поле сломает поиск:**
```java
Set<Product> products = new HashSet<>();
products.add(p);            // Product — ЭЛЕМЕНТ SET (= КЛЮЧ в HashMap внутри)
p.setPrice(...);
products.contains(p);       // ❌ НЕ НАЙДЁТ — Product теперь используется КАК КЛЮЧ
```
`HashSet` внутри — это `HashMap`, где элемент = ключ. Вот тут mutable hashCode фатален.

> **Формула: mutable hashCode опасен только у объектов-КЛЮЧЕЙ (или элементов Set). У значений Map (или элементов List) — не важно вообще.** Прежде чем паниковать про mutable hashCode — спроси себя: этот объект используется как ключ/элемент Set, или как значение/элемент List?

## 2. ⭐ Дерево в HashMap-бакете — от количества КЛЮЧЕЙ, не от размера значений

```java
Map<String, List<Order>> byRegion;   // 10 КЛЮЧЕЙ (регионов)
// в каждом List<Order> — по 50 000 заказов
```

**Ловушка:** думать, что 50 000 элементов в списке как-то влияют на структуру HashMap (дерево, бакеты).

**Правда:** для HashMap это просто **10 записей (Entry)** — хеш считается только от ключа `"North"`, `"South"` и т.д. Дерево (red-black tree) образуется, когда в **одном бакете** скапливается **≥8 Entry** (коллизия хешей **ключей**). У тебя всего 10 ключей на всю мапу — дерево тут вообще неактуально.

`List<Order>` с 50 000 элементами — это отдельный `ArrayList`-объект, на который значение просто **указывает**. HashMap про его содержимое ничего не знает.

> **Формула: размер объектов-значений НЕ влияет ни на бакеты, ни на скорость поиска по ключу.** Растёт только память под содержимым, структура и скорость Map — не меняются.

## 3. ⭐ ArrayList в многопотоке — не просто lost update, а поломка структуры

```java
private static final List<Long> latencies = new ArrayList<>();   // НЕ потокобезопасен
public void record(long ms) { latencies.add(ms); }   // из МНОГИХ потоков
```

**Механизм поломки (глубже, чем "гонка"):**
```java
// упрощённо, что делает add():
elementData[size] = element;   // 1. положить в ячейку
size++;                         // 2. увеличить счётчик
```
Два потока с `size=5` одновременно:
```
A: elementData[5] = свой элемент
B: elementData[5] = свой элемент   ← СТОЛКНОВЕНИЕ в одной ячейке, A затёрт
A: size++ → 6
B: size++ → 6   ← size ВРЁТ, должно быть 7
```
При одновременном **resize** (расширении массива) — риск `ArrayIndexOutOfBoundsException`, `ConcurrentModificationException`, null-дыры в массиве.

> **Формула: `ArrayList.add()` в многопотоке — не "недосчитались значений" (как с count++), а риск физического повреждения внутренней структуры** (столкновение в ячейке + рассинхрон size + возможные исключения). Собесный термин: непредсказуемое повреждение состояния.

## 4. ⭐ CopyOnWriteArrayList — только для РЕДКОЙ записи, не любой синхронизированной

```java
List<Long> latencies = new CopyOnWriteArrayList<>();
public void record(long ms) { latencies.add(ms); }   // вызывается на КАЖДЫЙ запрос — ЧАСТО
```

**Ловушка:** «add() у CopyOnWriteArrayList synchronized → значит безопасно → значит подходит».

**Правда:** безопасно — да. Подходит — **нет**. `CopyOnWriteArrayList` при **каждой** записи **копирует весь внутренний массив целиком**. Если список вырос до 100 000 элементов (метрики за время работы), каждый `add()` — это копирование 100 000 элементов. Под частой записью (тысячи раз в секунду) — катастрофические затраты.

> **Формула: "безопасно" ≠ "подходит для сценария". CopyOnWriteArrayList — read-heavy/write-rare** (списки слушателей, редко меняющиеся конфиги). Частая запись (метрики на каждый запрос) → противопоказание. Альтернатива: `ConcurrentLinkedQueue` (O(1) без копирования) или ограниченный буфер.

## 5. ⭐⭐ Утечка памяти ≠ регулярная нагрузка на GC (разные явления)

```java
public List<Product> getLowStock(List<Product> all, int threshold) {
    List<Product> result = new ArrayList<>();
    for (Product p : all) if (p.getStock() < threshold) result.add(p);
    return result;
}
// вызывается каждую минуту, годами, обрабатывает 2 млн товаров
```

**Вопрос-ловушка:** «вызывается годами — накопится ли деградация?»

**Разбор:**
- Если `result` **используется и забывается** после каждого вызова (не кладётся в growing static/кэш) — **накопления НЕТ**. Каждый вызов создаёт объекты → они умирают → GC собирает → следующий вызов с чистого листа. Память **не растёт со временем**.
- Реальная нагрузка — **разовая**, на каждый вызов: создание/сборка ~2 млн объектов может дать **заметную GC-паузу** (stop-the-world) в этот момент. Это не «деградация со временем», а **регулярный, но не растущий** всплеск.
- **Настоящая утечка** — другое: объект **навсегда** остаётся достижимым по ошибке (`result` кладут в growing static-список и не чистят) → **вот тогда** Old Gen реально растёт из месяца в месяц → неизбежный `OutOfMemoryError`.

> **Формула: разделяй "утечка" (объект навсегда недостижимо освобождается — растёт бесконечно, реальный риск) от "регулярная нагрузка без накопления" (каждый вызов независим, память возвращается, риск — только заметные паузы GC в моменте).** Первое лечится поиском забытой ссылки. Второе — мониторингом GC-пауз/батчингом, если объём слишком велик за раз.

## 6. ⭐⭐ Составные операции — гонка/несогласованность ЕСТЬ ДАЖЕ в ConcurrentHashMap

Мы это видели на `get()+put()` (блок 6 многопоточки). Тот же принцип — на `clear()+putAll()`:

```java
private final Map<String, BigDecimal> cache = new ConcurrentHashMap<>();

public void refresh() {
    cache.clear();                        // ← мапа СТАЛА ПУСТОЙ здесь
    cache.putAll(fetchLatestRates());     // ← заполнится только ЗДЕСЬ
}
// между этими строками — ОКНО, где cache ПУСТА

public BigDecimal convert(String currency) {
    BigDecimal rate = cache.get(currency);   // может вернуть NULL в этом окне!
    return amount.multiply(rate);             // 💥 NullPointerException у реального пользователя
}
```

**Ловушка:** «поставлю ConcurrentHashMap — и всё будет безопасно».

**Правда:** CHM защищает **каждую отдельную операцию** от структурной поломки. Но `clear()` и `putAll()` — **два отдельных вызова**, между ними **нет** атомарности — ровно та же проблема, что `containsKey`+`put` или `get`+`put`.

**Правильное решение — не мутировать существующую коллекцию, а атомарно подменить ссылку целиком:**
```java
private volatile Map<String, BigDecimal> cache = Map.of();

public void refresh() {
    Map<String, BigDecimal> newRates = fetchLatestRates();  // собрали НОВУЮ мапу целиком, в стороне
    cache = Map.copyOf(newRates);                             // ОДНА атомарная подмена ссылки
}
// convert() читает cache — либо ВСЯ старая, либо ВСЯ новая, НИКОГДА не пусто
```

> **Формула: ConcurrentHashMap ⇒ безопасность каждого метода, но НЕ атомарность их комбинации.** Для "заменить всё сразу, без промежуточного пустого состояния" — строй новую immutable-коллекцию в стороне и атомарно подменяй `volatile`-ссылку, а не мутируй существующую по частям (`clear`+`putAll`, `remove`+`put` и т.п.).

## Сводная памятка — вопрос перед ответом на любую задачу с коллекцией/памятью/потоками

| Спрашивают про... | Задай себе вопрос |
|---|---|
| mutable hashCode | Это КЛЮЧ (или элемент Set) — или значение (элемент List)? |
| дерево/бакеты HashMap | Дело в количестве КЛЮЧЕЙ, а не в размере значений? |
| гонка в коллекции | Что физически ломается — просто число, или структура (столкновение ячеек, size)? |
| выбор concurrent-структуры | Она безопасна ДЛЯ ЭТОГО паттерна нагрузки (частота чтения/записи), не просто "безопасна вообще"? |
| частый вызов метода в проде | Это накопительная утечка (навсегда достижимо) или разовая нагрузка без накопления? |
| CHM решает всё? | Комбинация ИЗ НЕСКОЛЬКИХ методов — есть окно несогласованности между ними? |

**Проверь себя:** пройдись по всем шести пунктам и объясни каждый своими словами, не подглядывая.
